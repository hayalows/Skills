# Visual Integrity Gate (v3.1)

Mandatory for new visual work, redesigns and visual audits. Touch work checks affected elements and adjacent regressions only. These rules adapt Google Gemini Frontend Design v1.0.0 (Apache-2.0); see the source map. They are design standards, not an AI-authorship detector. Do not claim a site was generated by AI based on appearance.

## Rules

| ID | Default requirement | Legitimate exceptions or protected meaning |
| --- | --- | --- |
| VI01 Opening | Tools, search, news, docs, dashboards and payments start with the real task or content. No marketing hero in front of it. Frequently used controls and initial result/feedback should fit a realistic first phone screen when possible. | Necessary disclosure, authentication, meaningful steps, keyboard or accessibility scaling. Record task visibility at the actual viewport. |
| VI02 Heading discipline | Start sections with a meaningful heading. Remove decorative eyebrows, kickers, duplicated titles and category labels above headings. | Real breadcrumb, article category/date, required identification or navigational context; prefer plain text in a useful location. |
| VI03 Honest status | Zero invented live dots, counters, ratings, badges, activity, urgency, or stock claims. Remove non-informational chips. | Genuine pending, verified, stale, unavailable, warning and data status must stay; real metadata may be plain text or a semantic badge. |
| VI04 Surface grouping | No nested card cages. Use whitespace, alignment, subtle tint or dividers as the first choice. | Distinct interactive boundaries, draggable items, repeated result groups or approved design system components with a demonstrated grouping benefit. |
| VI05 Typography | At most two authored font families; three active body sizes, four for genuinely dense tables/tools. H1/brand and one primary display value may be exempt when they are truly focal. Body paragraphs and lists share one readable scale. No visible text below 13 CSS px in the opening at default scaling. Use sentence case and tabular numbers where compared. | User-provided brand, content semantics, platform or accessibility needs; do not reduce text or hide information to hit the count. Count actual computed visible text roles at each width, not declared tokens or fallback font lists. |
| VI06 Actions | One primary action per content section; no repeated CTAs or button walls. Choices use connected tabs, radios, switches, select or direct manipulation. | Distinct task actions, cancel/back, safety confirmations, real controls, meaningful repeated row actions. Preserve keyboard semantics. |
| VI07 Numbering and copy | No decorative 01/02, fake chapter counts, synthetic scroll cues, slogan fragments, inflated claims, unnecessary ALL CAPS micro-labels or generated em-dashes. Use clear task labels. | Real steps, ranks, dates, accounting identifiers, acronyms, quotations and meaningful progress. Preserve supplied copy. |
| VI08 Composition and colour | Choose from the subject, not model reflexes. Reject default split hero with button pair and KPI footer, automatic beige/rust, neon gradients, repeated icon-card grids, uniform pills and generic glass/glow. A brand opening earns its expressive scale; utility opens directly. | Explicit approved visual brief or a proven task fit. Record why the composition fits this particular subject. Useful grids and rounded controls are not inherently defects. |
| VI09 Imagery and data | Use original, relevant assets or meaningful actual data; deliberate crop and light. No placeholder media, unlabelled decorative charts or generic graphics with no function. | Text-only tools are valid. Concept imagery must be labelled when factual confusion is possible. Charts have units, legend or direct labels and accessible values. |
| VI10 Motion | Native scroll for tools; explicit transition properties, brisk feedback (140–240ms starting point), no decorative endless movement, content visible at rest, reduced motion. | Meaningful progress indicators or requested functional animation. Longer narrative motion requires a usability and performance case. |
| VI11 Responsive integrity | No unintended page or nav overflow, clipped words, overlapped captions, hidden controls or sticky collisions. Inspect actual rendered text and controls. | Intentional independently scrolling tables or carousels with accessible controls and discoverability. Never hide overflow to disguise lost content. |
| VI12 Whole-page craft | Same coherent direction from opening to footer; inspect real scrolled viewports and meaningful alternate states. Do not fall back into a generic grid below the fold. | Repeated structure when content calls for it. All applicable evidence must be inspected; unknown is not a pass. |

Safety, accessibility, truthful data, approved brand and the core task outrank these defaults. Never erase a label, warning, real status, useful date or accessible name for visual neatness. No exception can waive an actual product, accessibility, safety or truth defect.

## Screenshot-first critic

For a Screen, inspect the affected screen at phone and desktop and its meaningful states. For a Flow or Product, review each key route and state in vertical slices. Use at least 360, 390×844, 768, 1280 and 320 reflow; include the final footer and scroll positions at normal viewport height. Review sticky navigation after scrolling, loading/error/empty states, long currency values and real data. Capture meaningful desktop and phone views of animated content at rest. Inspect the actual image, not merely a URL, alt text or generated description.

1. Start with screenshots without the author's explanation. If an independent reviewer/agent is available, provide screenshots, task and constraints but not the design rationale; otherwise perform a separate self-critique and label it as such.
2. Ask what the eye sees first, where the task begins, what the user has to read twice, and what visual surface adds no meaning. Compare subject fit with another category: would the same page work unchanged for an unrelated business?
3. Locate each finding by route, viewport, state and element. Record observable evidence, severity (task-blocking, major, minor), effect on the user, rule ID and concrete remedy. Aesthetic preference alone is not evidence of a violation.
4. Repair hierarchy, information structure and control placement before tweaking radius or colour. Reuse real data or subject-specific artwork instead of fake decoration. Preserve controls and constraints. Fix the most material issues first.
5. Re-render affected states and adjacent views. Confirm the defect is gone and did not produce a new one. Compare pre/post at the same width and state. Do not count a deployment as a fix until the final revision is inspected.

## Gate record and release decision

One row per applicable rule: ID | route/state/viewport | evidence (seen, operated, measured or read) | status | reason or issue | remedy | retest evidence.

Statuses: PASS, FAIL, EXCEPTION, NV (not verified), NA (not applicable). An exception requires the concrete user or brand need, exact scope, evidence, and why a simpler compliant alternative would harm it. A permitted exception is not permission to ignore a broken task. NA requires a reason. A rule cannot PASS solely because static lint did not flag it. The visual gate passes only when all applicable rules pass or have justified exceptions; FAIL or NV blocks a visual pass. For an audit, report these findings without editing unless asked. Do not block unrelated Touch work on historic out-of-scope violations; report them separately.

Run static visual warnings via ui-lint and the browser probe at the checked viewport/state. They generate leads, not a verdict. Inspect the actual page to confirm them. Report measurements with evidence, not invented scores. A successful production build and a screenshot URL are not visual approval. If a user authorizes publishing despite known limitations, state the unresolved risks and verification status before claiming readiness; do not claim a passed gate.

## Machine-checkable record

For Screen, Flow or Product work with a shell, save a JSON report alongside review evidence and run:

```bash
node product-design-os/scripts/visual-gate.mjs report.json
```

Structure: `{"surfaces":[{"name":"route / state","rules":[{"id":"VI01","status":"PASS","scope":"390×844, default","reason":"Observed primary control before scrolling","evidence":[{"kind":"seen","ref":"home-390.png"}]}]}]}`. This is a shape example, not a complete report or an actual test result. Include every VI01–VI12 record per surface, marking out-of-scope checks NA with reasons. An EXCEPTION also requires `need` and `alternative` text. For a repaired defect, set `fixed:true` and include `retest` evidence records. Record different viewport/state observations together where appropriate. The checker rejects missing and duplicate rule records, FAIL/NV, missing rationale, source-only visual passes, unjustified exceptions and missing retest evidence. It cannot verify whether the screenshots exist, are current, show all needed states, or support the claim; reviewers must inspect them. A clean report does not waive accessibility, product or visual judgment.

## Calibration examples

- Calculator: remove the slogan, duplicate section title and inset result cage. Keep amount labels, exchange-rate caveat and source date. Use space saved to reveal the first estimate.
- News: retain meaningful article categories and dates; remove a promotional hero ahead of the stories.
- Checkout: keep pending status, amount, fees, recipient, cancel and retry safety even if they increase visual density.
- Budget: replace an enormous empty number panel with a labelled real spending breakdown. Ensure the legend does not inherit headline styling.
- 3D education: move caption into actual layout space rather than overlaying a model; real chapter progress is allowed.
- Portfolio: removing badges alone is not art direction. Create a memorable composition, real project evidence and visual rhythm across case studies.
